# 第四部分 · 待你拍板的两个决策

## 决策 1：`_work_dev` 要不要接上远端？
- **推荐：接。** 先推一个保险分支（§1.9 第 1 步），再让 AutoClaw 从 `feat/*` 分支干活、开 PR 到 `dev`。
- 不接的后果：AutoClaw 只能本地提交，**队友看不到、也无法 review**，而且本机是唯一副本。
- ⚠️ **接上后的纪律**：`_work_dev` 的内容**领先于**远程 `dev`（远程 `dev` 还缺空间线 #23、方法库 #34、健康库等）。
  **绝不能在 `_work_dev` 里 `git add -A` 后推给 `dev`** —— 那会造出一个吞掉所有人工作的巨型 PR。
  正确姿势：**只 stage 你自己改的那几个文件**，推 `feat/*` → PR 到 `dev`。

## 决策 2：AutoClaw 在 `_work_dev` 干活，还是新 clone 一份远程 dev？
| 方案 | 优点 | 代价 |
|---|---|---|
| **A. 直接用 `_work_dev`（推荐）** | 拿到全部最新成果（空间线/方法库/健康库）；不用重装依赖 | 与远程分叉，必须严守「只提交自己改的文件」 |
