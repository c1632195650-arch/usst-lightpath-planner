## 一、定位

**梨宝是这个产品的"大脑与对话层"**——它认识你的课表，了解上理工的真实生活细节，在「信息 / 引导 / 建议 / 决策」四层边界内给你量身定制的回答。

| | 梨宝 | 通用聊天机器人 | 普通校园问答 |
|---|---|---|---|
| 知识来源 | 515 篇上理官方文档（可溯源） | 模型参数记忆 | 关键词匹配 FAQ |
| 边界感 | 知道自己"答不了"，会诚实说并切换 | 不懂也编 | 答不了就沉默 |
| 个性化 | 画像 + 长期记忆 + 空间上下文 | 无 | 无 |
| 上理坐标 | 每个回答带具体坐标（三教→一食堂 3 分钟） | 泛泛而谈 | 无 |

**不是什么**：不是排程工具的外壳，不是套壳问答。排程只是它的一种输出形式。

## 二、当前已落地（可验证）

### 架构

```
前端 React（月历 / 梨宝 / 画像 三 Tab）
        ↓ HTTP
FastAPI 后端（server/app.py）
   ├── 检索层  scripts/rag.py      FTS5 + 向量混合
   ├── 记忆层  server/memory.py    长期画像 / 会话摘要 / 短期原文
   ├── 空间层  server/campus.py    60 POI 校园空间图谱
   └── 生成层  DeepSeek（可降级抽取式）
        ↓
SQLite（usst_articles.db + libao_memory.db）
```

### 一次问答发生了什么

1. **检索**：jieba 分词 → FTS5 BM25（权重 0.4）+ bge-small-zh 向量（权重 0.6）× 时效因子；查询扩展把口语转成官方术语（"大功率"→"违规电器/额定功率"）
2. **边界判定**：取 **top3 里最高的 raw_vec**（不是 top1——数据翻倍后 top1 常是"较新但不相干"的文档，实测光电杯查询 top1=0.493 噪音、top2=0.700 正确答案）
3. **三档路由**：
   - `grounded`（raw ≥ 0.68 且为事实型）：严格引用官方文件
   - `hybrid`（raw ≥ 0.56）：RAG 给事实 + LLM 给方法，语气区分官方与经验
   - `llm`（raw < 0.56）：坦白"这个学校没明文规定"，再以过来人身份给建议
   - **人设从不切换，只切"依据约束"**——所以用户感觉不到割裂
4. **记忆拼接**：长期画像 + 增量会话摘要（每 4 轮压一次，不是每轮重算）+ 短期原文
5. **生成**：DeepSeek + 梨宝人格 system prompt；无 Key 自动降级为抽取式

## 三、预期演进路线

### 短期：把"骨架"立住（骨架优先于算法）

| # | 任务 | 为什么先做 |
|---|---|---|
| 1 | **契约补齐**：`types.ts` 加 `Phase` / `WeekPlan` / `TimeBlock` / `Task` | 纯类型定义，不碰算法 UI，**零返工风险**；它是你和队友分工的交汇点 |
| 2 | **适配层** `scheduleToBlocks`：队友的 `Schedule` → 幕墙 `blocks`（时间/名称/密度/颜色） | 约 80 行，让 Newton 从"显示 mock 三版"变成"显示你的真实课表" |
| 3 | 前端接 `session_id` | 目前多轮只在后端，App 里要连续对话需稳定 session |

**为什么骨架优先**：你自己点破过——"没有数据或案例能验证算法贴合用户心意"。所以诚实策略是**把"可调"做成核心能力，而不是把"算得准"做成核心能力**。算法可以后补（先规则、后 LLM、再混合），但"预览 → 选版 → 局部调整"这个交互骨架必须先立住，因为它决定数据结构和 UI，改一次成本高。

### 中期：能力填充

| # | 任务 | 方向 |
|---|---|---|
| 4 | **排程引擎** | 规则生成骨架（保证课表不错、不冲突）→ LLM 生成 3–4 个风格不同版本 → 用户挑一个 → 局部微调（C+D 混合） |
| 5 | **画像驱动的主动引导** | 学得慢的人期末周提前；新生迷茫时给"探索清单"而非日程表 |
| 6 | **空间深度整合** | 每个时间块带上理坐标：三教下课 → 一食堂 3 分钟 → 今天有酱鸭；自习 → 湛恩图书馆 7 点开门 |

## 四、技术约束与已知风险

| 项 | 现状 / 风险 | 应对 |
|---|---|---|
| **路由阈值** | 0.68 / 0.56 是在 515 篇规模下调的；数据量再翻倍会失效 | 用 `analyze_coverage.py` 复跑体检，重新校准 |
| **GPU** | RTX 5070 的 NVML 不可用，向量走 CPU ONNX | 够用（1645 块）；量大再优化 |
| **隐私** | `libao_memory.db` 含个人信息 | 已 gitignore，**绝不能进仓库**；API Key 同理 |
| **成本** | DeepSeek 调用便宜 | 演示阶段可忽略 |
| **智能边界** | LLM 容易"替用户做决定" | 四层约束写进 prompt；决策层绝不拍板 |
| **有后端的代价** | 放弃"数据不出设备"这个隐私钩子 | 已在产品层面接受，换真正智能 |
