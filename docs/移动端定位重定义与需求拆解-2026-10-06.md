> **性质**：这不是需求列表，是**定位翻转**的记录。上一版移动端是「网页端的搬运工」，

> **状态**：**已拍板（2026-10-06 CY「接受」）**——定位翻转与 §9 八项按本文倾向生效；定稿口径已登记 project-core.md §6.5（唯一权威）。本文档转为历史拆解记录。

## 0. 一句话定位（本文档的地基）

> **网页端负责「想清楚」，手机端负责「做出来」。**
> 手机不是网页的小屏版，是**执行层的仪器**——单手、竖持、碎片时间、��览一眼就能行动。

**判别标准**（后续所有设计争议都拿这条判）：
- 在网页端能完成的事 → 不该在手机上做（例：整周重排、课表导入、梨宝对话）
- 用户在手机上**正在做一件事** → 手机必须立刻给出「现在做什么、还剩多久、下一步是什么」
- 手机上产生的**动作**（勾完成、写待办、记一笔）→ 必须能回传，让网页端的下一次计划更准

### 1.1 三层分工（不可越界）

| 层 | 载体 | 职责 | 不做 |
|---|---|---|---|
| **规划层** | 网页端 | 整周重排、目标拆解、梨宝对话、课表管理、画像 | — |
| **执行层** | **手机端** | 今日单日、当前块、待办打勾、习惯养成、执行力自评 | 整周重排、课表导入、画像编辑 |
| **数据层** | 服务端 | 同步、ICS、习惯库、评估题库 | — |

**梨宝要不要上手机？我的判断：不要**（详见 §3.2），但保留一个**极简指令入口**。

## 1. 三个即时技术问题的答案

### 1.1 「没看到注册/登录入口」→ 是白屏，已定位并修

**根因链**：
1. 线上 `dist/` 还是 **10-03 的旧构建**（`mobile-DLn5QG6u.js`）
2. APK 内是新构建（`mobile-DyljSmqt.js`）
3. `capacitor.config.ts` 的 `server.url = http://101.35.253.143` → WebView **加载公网页面**而非包内资源
4. 线上旧包 + 当前代码不匹配 → JS 运行时错误 → **白屏**（登录页本该是首屏，出现即代码没跑起来）

**已做**：把最新 `dist/` 部署到服务器，线上现已是 `mobile-DyljSmqt.js`，与 APK 内一致。
**你验证**：强杀 App 重开。若仍白屏 → 见§1.1.1。

> ⚠️ **这是我的运维疏漏**：APK 指向公网，线上前端就必须与 APK 版本同步，而我昨天只传了 APK 没传 dist。

#### 1.1.1 万一还白屏：30秒判别法

在手机浏览器直接打开 `http://101.35.253.143/m.html`：
- **能出登录页** → 服务器正常，问题在 APK/WebView（清数据重装：`设置→应用→光溯→存储→清除数据`）
- **也是白屏** → 服务器侧问题，把浏览器报错截图发我

若浏览器能显示但 APK 白屏，**大概率是 WebView 缓存了旧资源** → 清除应用数据重来。

### 1.2 「手机时间没法调」→ **不要调时间，改用测试块**

你说得对，调系统时间不现实（要关闭自动时间、可能锁屏密码、进设置深处）。

**正确做法：造一个「20 分钟后开始」的块。**

| 路径 | 做法 |
|---|---|
| **网页端**（推荐） | 排计划时把某块的开始时间设成 20 分钟后（网页端时间随便填） |
| **更省事** | 走 ICS 验证：网页端生成 ICS 链接 → 手机系统日历订阅 → 在日历里造一个 20 分钟后的日程（**系统日历的提醒与 App 无关，可独立验证通知链路**） |

> 但要注意：**ICS 是系统日历通道，不验 App 的本地通知**。
> 验 App 通知最快的办法是——在网页端排一个**当前正在进行**的块（开始时间 = 过去 5 分钟，结束 = 未来 60 分钟），打开 App 立刻能看到「正在进行」横幅；把手机时间往后调1 小时不必要，但**要确保块的时间窗覆盖此刻**。

**结论**：走查阶段 C 改成「**造覆盖当前时刻的块**」，不调时间。

## 3. 范围裁决：不做 / 做 / 待斟酌

### 3.1 明确**不做**（移回网页端）

- 整周重排（引擎职责）
- **课表导入**（你说「课表导入有问题，课表窗口也删掉」→确认移除）
- **画像窗口**（你说「不要有画像窗口」→ 确认移除）
- 梨宝完整对话流（见 §3.2）

### 3.2 梨宝要不要上手机？—— 我的建议：**不上完整版，只留一个指令条**

**理由**：
1. 梨宝是**规划期**工具：需要长文本输入、看回复、迭代追问 → 竖持单手体验差
2. 会把「执行器」稀释成「聊天窗」，破坏 §1 的定位
3. 移动端已有 F11 快捷指令占位（「今天还有啥」「帮我顺延下一块」）→ 这是**执行型**指令，不是规划型

**建议方案**：Today 页保留一条**极简指令栏**（一行输入 + 一枚发送），只接**执行型意图**：
- 「顺延下一块 15 分」「把高数标完成」「今天还有啥」→ 直接改覆盖层 + 重排，**不调 LLM**
- 复杂规划（「我这周怎么排」「帮我调整目标」）→ **引导到网页端**：提示"这个在电脑上问我更方便"

> 若你想要「梨宝全上手机」，我需要你确认——那是**另一个量级的工作**（对话流 + 上下文 + 流式输出 + 竖持输入体验），且会牺牲执行器的信息密度。**我倾向不做，等你拍板。**

### 3.3 待你确认的三点

| # | 议题 | 我的倾向 |
|---|---|---|
| ① | 梨宝完整对话上不上手机 | **不上**，只留执行型指令栏 |
| ② | 待办要不要真的做**双向同步**（手机写→网页看） | **要**，你原话「同步一下」，且待办是跨端高频 |
| ③ | 习惯库建库规模 | 先做**最小可用集**（见 §6），不追求一次做全 |

## 4. 待办与目标（新增模块）

### 4.1 概念区分

| | 待办（Todo） | 目标（Goal） |
|---|---|---|
| 周期 | **短期**（今天/本周可完成） | **中长期**（学期/季度） |
| 数量 | 多（5-15） | 少（1-3） |
| 完成 | 打个勾即完成，**不填时间** | 完成时**要求填具体完成时间**（粗粒度，如「2026 年 9 月上中下旬」） |
| 目的 | 即时成就感「办完一件事」 | 防遗忘，长期追踪 |
| 类比 | 购物清单 | 学期目标 |

**「中长期待办要填完成时间」的理由**（你原话：怕用户忘了打勾）→强制留痕 + 后续可统计达成率。

### 4.2 交互（你给了两个方向，我合并成一套）

- **左滑手势**：在待办条目上左滑 → 露出「完成 / 编辑」快捷动作
- **显式按钮**：目标卡右上「+」→ 打开新增面板（标题+ 类型+ 可选截止）

**布局**：
```
┌─ 目标卡（长期，1-3 条）──────────┐
│ 目标：期末把高数刷到 90    [+]  │
│  进度：░░░░░ 1/5 阶段           │← 手动推进 or 关联待办自动折算
└────────────────────────────────┘
┌─ 最近待办（今天就能做）───────────┐
│ ☐ 交高数作业第 3 章    ←划 ┆★ │
│ ☐ 跑步 3km                      │
└────────────────────────────────┘
┌─ 中长期待办（要填完成时间）──────┐
│ ◻ 读完《学习之道》  [完成时间: ]│← 勾时必须填
└────────────────────────────────┘
```

### 4.3 首次进入的「浮现卡」

- 首次登录后/ 每早首次打开 → **目标 + 待办小卡**从顶部滑入
- **自动消失**：约 4 秒后淡出（或上滑收起）
- **不自动消失的情形**：有待办即将到期 / 有目标逾期 → 转为常驻提示条
- 也可手动下划收起

### 4.4 数据与闭环（**这是你强调的重点**）

```
手机端写待办/目标
   ↓ 本地覆盖层（乐观写入，立刻见勾）
   ↓ PUT /api/sync/state（复用现有同步通道，schemaVer+1）
   ↓ 云端
网页端读到 → AI/引擎排计划时把待办当硬约束
   ↓
手机端再同步 → 显示「已被排进今天几点」
```

**关键约束**：手机端**不本地排计划**（决策基线 §5 不变），只做「记录 → 同步 → 看结果」。

> ⚠️ **待办需要 schemaVer+1**（新增 `todos[]` / `goals[]` 字段）。
> 这动了 `SyncState` 契约——按红线必须**CY 拍板**，且客户端要「忽略未知字段」以保前向兼容。
> 网页端目前**没有**待办功能（你说「电脑端似乎还没有」），需要一并设计（网页端只读+ 简单新增，不做排程）。

## 5. 执行力 / 自控力评估（新增模块）

### 5.1 定位
- **不是**单次打分，是**长期趋势** + **可执行的改进建议**
- 题目来自**习惯库**（§6），保证「有依据的科学方法」，不是拍脑袋问「你自律吗」

### 5.2 采集机制（你定的规则）
- **每天首次打开 App** → 弹一次采集
- **最多 5 道题**（你说「不宜多」）
- 题目来源：按用户当前的**中长期待办 + 最近待办**类型，从习惯库抽相关题
  - 例：有「跑步」待办 → 抽运动坚持/习惯养成相关题
  - 例：有「背单词」待办 → 抽学习习惯/记忆方法相关题
- 目的是给评估体系提供**依据**（不是直接问「你执行力几分」）

### 5.3 评估维度（多维，长期个人提升）

| 维度 | 关注 | 数据来源 |
|---|---|---|
| 任务完成率 | 近期待办勾选比例 | 待办完成记录 |
| 拖延指数 | 中长期待办的实际完成时间 vs 计划 | 中长期待办的完成时间戳 |
| 连续性 | 习惯/目标的连续天数 | 完成记录历史 |
| 自我报告 | 题库采集（习惯库方法论） | 每日 5 题 |
| 时间纪律 | 计划块的实际开始 vs 计划 | 块完成时间 |

**输出**：不给「综合总分」（项目已有纪律：禁止综合总分，各维度本可互相补偿）。
改为**分维度曲线 + 一句「本周最该改的一件事」+ 指向习惯库里的具体方法**。

> ⚠️ 必须尊重项目既有原则：**`unknown` 绝不降级为 `gap`**（用户没做 ≠ 用户做不到），
> 缺数据用「不可信哨兵」而不是 0。

### 5.4 评估窗口（你原话「窗口专门评估执行力自控力」）

- Today 页**不下拉到底**的一个独立折叠区（避免干扰执行）
- 入口：Today 页底部「我的执行状态」→ 展开看五维曲线 + 本周建议

## 6. 习惯库（新增知识库，与现有库平等）

### 6.1 现状
- 现有：`method_kb.db`（方法库）+ `health_kb.db`（健康库）
- 你要的：**习惯库**（习惯养成 / 目标达成的权威科学方法）

### 6.2 与现有库的关系（你明确要求）

> **「如果健康库或者学习库有重叠内容统一归到习惯库里面」**

即：习惯库是**上层主题库**，健康库里「作息/运动坚持」类、学习库里「复习习惯」类→ **归入习惯库**，避免三库重复。

**建议**：
- 习惯库收编**方法论类**内容（行为改变、习惯养成、动机、执行力方法）
- 健康库留**生理健康类**（疾病、营养数据、健身动作）
- 重叠内容**单一来源**（存习惯库，健康库按需引用 id，不复制）

### 6.3 接入方式（与四大库平等）
- 检索层：习惯库注册进现有 RAG 检索管道（与 method/health 同等权重）
- 排程引擎：Tips 生成时**可被检索调用**（§7 当前块 tips）
- 梨宝：网页端对话时可检索习惯库
- 评估：题库**从习惯库抽题**

### 6.4 规模建议（最小可用集，先不做全）

> 你原话「不同种类习惯养成或不同目标达成的权威科学方法」——这个范围很大。
> **我建议 v1 只做 3 类 × 每类 5-8 条 = ~20 条**：
> 1. 习惯养成类（启动、微习惯、环境设计）
> 2. 拖延与执行类（两分钟法则、意图实施）
> 3. 目标达成类（目标分解、里程碑、复盘）

详细建库另开任务（含金标与门禁，见 DETAIL 的 KB 流水线）。

## 附二：勘误与任务分工（2026-10-06 02:50 追加，**以此节为准**）

> 本文档 §6.3 与 §3.2 有两处口径经CY 拍板后变更。**zcode / 后续 agent 读本文档时必须先读本节。**

### 勘误 1 · 习惯库 → **方法库升格**（原 §6.3 作废）

**原写**：「习惯库 v1 最小集约 20 条」→ **作废**。CY 明确要求习惯库
「**不要做最小的，要做尽可能科学的、实用的、具有指导价值的**」。

**事实核查结论**：项目实际有**四个库**，不是原文所写的两个：

| 库 | 载体 | 回答什么 |
|---|---|---|
| 上理库 | `data/usst_articles.db` | 学校有什么 |
| **方法库** | `data/method_kb.db`（**42 条**） | 该怎么学 |
| 健康库 | `data/health_kb.db` | 身体怎么了 |
| 空间库 | `data/campus_map.json` + `campus_network.py` | 怎么走 |

**方法库里已经躺着**自我决定论、内驱力、拖延调控、实施意图、习惯回路、元认知、认知负荷、双重编码、心流
—— **它本身就是"习惯与方法库"**，只是当前定位在「学习方法」。

**CY 已拍板：升格，不新建。** 理由：重叠内容单一来源、复用全部基建（证据分级A–D /引文核验 / 伪科学黑名单 /
金标门禁 / 编译链）；且有实证教训——42 条方法灌进上理库会导致 3/20 方法类查询被路由劫持
（`docs/method-kb-plan.md` §1）。

**注意**：健康库的**生理内容留在健康库**（它有 `guard()` 安全护栏，迁移会破坏"先守门再检索"）；
「重叠归习惯库」指的是**方法论类**内容。

→ 详见 **`docs/任务一-习惯与方法库升格方案-交zcode-2026-10-06.md`**

### 勘误 2 · 梨宝 → **方向 B**（原 §3.2 结论变更）

**原写**：「不上完整版，只留执行型指令栏」→ **作废**。CY 指出：阉割成一行指令栏「意义不到了」。

**CY 已拍板：方向 B —— 完整对话 + 四库问答，抽屉式入口，砍掉排程权。**

- **保留**：多轮对话、上下文、流式输出、四库 RAG 问答
- **砍掉**：改计划 / 重排 / 动课表（这些只在网页端）
- **入口**：Today 页的**抽屉**，不占主视觉
- **成本修正**：CY 指出这是「另一个量级」过重，实为**中等量级**（约 2-3 天，含流式与移动端输入法踩坑）
- **技术现状**：`/api/chat` 已有 `session_id` 多轮上下文 + `/api/chat/history`，
  **但无流式（SSE）** → 需加流式

### 勘误 3 · Tips 口径（原 §7 补充）

**CY 补充**：「当前块 Tips 更多给**方法论、价值观、认识论**相关的，这样适配性比较强，
因为**大学学科太多，很难覆盖完整**。」

→故`methodTipForBlock()` **不接受学科参数**，只接受块类型与时长特征。
跨学科通用是硬要求，不是取舍。

### 勘误 4 · 评估体系铁律（补充）

三条来自项目既有纪律，**必须以类型与断言落地，不靠自觉**：
1. **不给综合总分**（各维度本可互相补偿，压成一个数= 替用户做价值判断）
2. **`unknown` 绝不降级为 `gap`**（用户没做≠ 用户做不到）
3. **缺项用「不可信哨兵」而非 `0`**，分数必须与「可判度」同时出现
