# 技术决策记录（ADR）

> 答辩时被问"你为什么这么做"，直接翻这个文件。
> 每条都是**主动选择**，不是能力不足。讲清楚取舍 = 专业性。

---

## ADR-001 为什么只做 Web，不做 App

**决定**：只做响应式 Web + PWA，不做原生 App，不做套壳。

**理由**
1. 团队 2 人、技术起点为零、周期 20 天。双端 ≈ 两份工作量 + 两份 bug。
2. 评委通过浏览器/投屏看演示，Web 是最稳的形态。
3. PWA 已能覆盖"安装到主屏、离线使用、全屏无地址栏"这些用户对 App 的核心诉求。

**代价**：无法调用系统通知、蓝牙、后台定位。本产品不需要。

**对外话术**："采用 PWA 架构，一套代码覆盖桌面与移动双端，避免了双端重复开发与版本分裂。"

## ADR-002 为什么不用 Next.js

**决定**：用 Vite + React，不用 Next.js。

**理由**
1. Server Component / Client Component 的边界是 AI 生成代码的重灾区，报错信息（如 hydration mismatch）对新手极不友好。
2. 本项目无后端、无 SEO 需求，Next.js 的核心优势用不上。
3. 20 天里最稀缺的资源是"能自己修 bug 的时间"，不应消耗在框架心智负担上。

**代价**：失去 SSR 能力（本项目不需要）；未来要加后端时需另行搭建。

## ADR-003 为什么纯前端、不做后端和账号系统

**决定**：数据全部存浏览器 localStorage/IndexedDB，不上传服务器。

**理由**
1. **合规**：课表能定位一个人在特定时间的物理位置，属个人信息。不上云则无需隐私协议备案、无需处理删除请求、不存在数据泄露风险。这是刻意的合规设计，不是偷懒。
2. **成本**：免去服务器、域名备案、运维。
3. **可用性**：断网可用——答辩现场网络不可控。

**代价**：多设备不同步；换浏览器数据丢失（已提供导出/导入 JSON 备份缓解）。

**对外话术**："采用 Local-First 架构。学生的课表与学习数据不离开本人设备，从架构层面消除隐私风险。"

## ADR-004 为什么规则引擎为主、大模型为辅

**决定**：阶段划分、优先级、排程、期末分配全部用确定性规则实现；大模型只负责"结果解读"和"开放式提问"，且必须可降级。

**理由**
1. **可解释性**：评委一定会问"你的算法依据是什么"。规则引擎能逐项拆解说明，黑盒 LLM 答不上来。
2. **可复现**：同样的输入必须得到同样的输出。
3. **可用性**：无 Key、无网络时产品必须完整可用。

**代价**：相比纯 LLM 方案，灵活度较低。

**对外话术**："核心决策用确定性算法保证可解释与可复现，大模型只用于自然语言交互层，二者通过降级机制解耦。"

## ADR-005 为什么考试周留白率不降反升（22% → 30%）

**决定**：S3 冲刺期留白 22%，进入 S4 考试周反而上调到 30%。

**理由**
1. 考试周继续压缩休息会损害记忆巩固与考场发挥，边际收益为负。
2. 这是本产品与所有"帮你把日程塞满"的竞品的核心差异。
3. 它体现了一个判断：**产品指标不是"安排了多少学习小时"，而是"计划被执行了多少"。**

**代价**：可能被误解为"不够进取"。答辩时要主动讲，不要藏着。

## ADR-006 为什么不用 MBTI 做性格评估

**决定**：自建 12–15 题问卷，只问可观测行为，不做 MBTI 类型划分。

**理由**
1. MBTI 重测一致性低、信效度在心理学界争议大，用它做规划不可靠。
2. 类型标签（如 INFP）对"排日程"没有直接指导意义；而"你通常几点效率最高"有。
3. 心理测评属敏感个人信息，问得越少、越不标签化，合规风险越低。

**对外话术**："我们放弃类型学评估，改用行为锚定问卷——因为我们要预测的是'什么时候学'，不是'你是谁'。"
