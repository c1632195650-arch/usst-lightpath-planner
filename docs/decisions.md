# 技术决策记录（ADR）

> 答辩时被问"你为什么这么做"，直接翻这个文件。
> 每条都是**主动选择**，不是能力不足。讲清楚取舍 = 专业性。

## ADR-001 为什么只做 Web，不做 App

**决定**：只做响应式 Web + PWA，不做原生 App，不做套壳。

**理由**
1. 团队 2 人、技术起点为零、周期 20 天。双端 ≈ 两份工作量 + 两份 bug。
2. 评委通过浏览器/投屏看演示，Web 是最稳的形态。
3. PWA 已能覆盖"安装到主屏、离线使用、全屏无地址栏"这些用户对 App 的核心诉求。

**代价**：无法调用系统通知、蓝牙、后台定位。本产品不需要。

**对外话术**："采用 PWA 架构，一套代码覆盖桌面与移动双端，避免了双端重复开发与版本分裂。"

---

## ADR-002 为什么不用 Next.js

**决定**：用 Vite + React，不用 Next.js。

**理由**
1. Server Component / Client Component 的边界是 AI 生成代码的重灾区，报错信息（如 hydration mismatch）对新手极不友好。
2. 本项目无后端、无 SEO 需求，Next.js 的核心优势用不上。
3. 20 天里最稀缺的资源是"能自己修 bug 的时间"，不应消耗在框架心智负担上。

**代价**：失去 SSR 能力（本项目不需要）；未来要加后端时需另行搭建。

## ADR-003 为什么纯前端、不做后端和账号系统

**决定**：数据全部存浏览器 localStorage/IndexedDB，不上传服务器。

**理由**
1. **合规**：课表能定位一个人在特定时间的物理位置，属个人信息。不上云则无需隐私协议备案、无需处理删除请求、不存在数据泄露风险。这是刻意的合规设计，不是偷懒。
2. **成本**：免去服务器、域名备案、运维。
3. **可用性**：断网可用——答辩现场网络不可控。

**代价**：多设备不同步；换浏览器数据丢失（已提供导出/导入 JSON 备份缓解）。

**对外话术**："采用 Local-First 架构。学生的课表与学习数据不离开本人设备，从架构层面消除隐私风险。"

## ADR-004 为什么规则引擎为主、大模型为辅

**决定**：阶段划分、优先级、排程、期末分配全部用确定性规则实现；大模型只负责"结果解读"和"开放式提问"，且必须可降级。

**理由**
1. **可解释性**：评委一定会问"你的算法依据是什么"。规则引擎能逐项拆解说明，黑盒 LLM 答不上来。
2. **可复现**：同样的输入必须得到同样的输出。
3. **可用性**：无 Key、无网络时产品必须完整可用。

**代价**：相比纯 LLM 方案，灵活度较低。

**对外话术**："核心决策用确定性算法保证可解释与可复现，大模型只用于自然语言交互层，二者通过降级机制解耦。"

## ADR-005 为什么考试周留白率不降反升（22% → 30%）

**决定**：S3 冲刺期留白 22%，进入 S4 考试周反而上调到 30%。

**理由**
1. 考试周继续压缩休息会损害记忆巩固与考场发挥，边际收益为负。
2. 这是本产品与所有"帮你把日程塞满"的竞品的核心差异。
3. 它体现了一个判断：**产品指标不是"安排了多少学习小时"，而是"计划被执行了多少"。**

**代价**：可能被误解为"不够进取"。答辩时要主动讲，不要藏着。

## ADR-006 为什么不用 MBTI 做性格评估

**决定**：自建 12–15 题问卷，只问可观测行为，不做 MBTI 类型划分。

**理由**
1. MBTI 重测一致性低、信效度在心理学界争议大，用它做规划不可靠。
2. 类型标签（如 INFP）对"排日程"没有直接指导意义；而"你通常几点效率最高"有。
3. 心理测评属敏感个人信息，问得越少、越不标签化，合规风险越低。

**对外话术**："我们放弃类型学评估，改用行为锚定问卷——因为我们要预测的是'什么时候学'，不是'你是谁'。"

## ADR-007 · 评分口径灰度：`legacy` / `transfer-aware`（2026-09-19，CY）

**背景**：实测 transferRisk 占总代价 **90%**，而它的实现是「地点一变就固定罚 1」——
与步行距离、校区、真实时间**全都无关**（实测 170/170 个"地点变化对"全是固定罚；
注入真实分钟后显示真正紧张的 **0 对**）。等于引擎在罚「换了几次地点」，而真正危险的
跨校区排布（1km）与隔壁楼（100m）同价。

**决定**：新增 `ScoringMode`，**默认 `legacy`**（逐位保持旧行为），新口径显式开启。

**理由**
1. 改评分会改变 `tests/golden/*.json`（2026-09-15 冻结语料）的 cost 数值。直接翻默认等于
   让 5 份冻结快照"失效"，而快照是 AC-2/AC-3 的验收基准 —— 不能单方面推翻。
2. 灰度档让新旧并存：legacy 保快照有效、可随时回归；新档另拍基线、逐步验证。
3. 度量升级与搜索升级要分开验证（实测：只改度量时**计划逐块不变**、只是分数从 119 变 185
   → 说明 `improve` 尚未消费新度量，必须配套 P2）。

**同时决定的两件事**
- **可信度折扣**（`TRANSFER_TRUST = 0.8`，估算数据再 × `ESTIMATE_TRUST = 0.75`）：
  我方 OSM 路网经 `npm run audit:transfer` 实测**系统性偏长 30~100%**（8/8 矛盾同向，
  如 二公寓→思餐厅 595m vs 高德 288m）。直接用会**放大**风险 → 引擎过度保守。
  折扣是**明确、可撤销**的补偿；路网修好后把常量改回 `1.0`。
- **`TransferHint` 补入 `reliable` / `source`**：此前这两个信息只被写成一句中文 `note`，
  机器读不到（评分与 UI 都只能做字符串匹配，很脆）。

**代价**：多一个开关维度，需要测试覆盖两种口径（已加 5 条冻结锚点防 legacy 漂移）。

### ADR-007 附记 · 灰度结束：默认口径已翻为 `transfer-aware`（2026-09-19）

**决定**：`DEFAULT_SCORING = 'transfer-aware'`。`legacy` 仍可显式指定，5 条冻结锚点测试继续钉住它。

**为什么可以安全翻**（已核实的事实）：golden 快照与它们的比对走
`buildWeekPlan → construct`（旧 7 步），**根本不经过 `solveWeek`/`evaluate`** ⇒
快照与默认口径无关、逐位有效。翻转后 **262 个测试（109 + 153）全绿**，印证了这一点。

**如实记录的代价**：aware 档每次求解比 legacy 慢 **~2.7×**（p50 合计 19ms → 53ms）——
评分要逐对向 provider 问分钟数。三条降本尝试（候选级校验 / 候选剪枝 / provider 记忆化）
**全部实测否决**，理由见 `engine-optimization-paths.md` §三·八。

**配套**：引擎基线 `evals/runs/engine_baseline.json` 现在自带 `scoring` 字段 ——
毫秒数**只在同一口径下可比**，不记口径就是在做苹果比橘子的对比。

**对外话术**："我们没有直接改评分口径上线，而是加了灰度开关：旧口径保住冻结基准，
新口径先跑证据——实测把 90% 的代价从'换了几个地点'改成'这段路赶不赶得上'。"

## ADR-008 · improve 与 construct 的耦合，以及「候选评估前必须重挂转场提示」（2026-09-19，CY）

**背景**：PR-A 把评分改成能看真实转场分钟后，实测发现 `legacy` 与 `transfer-aware` 产出的计划
**逐块完全相同**。逐层排查出三个原因，缺一不可：

1. `improve` 没有转场数据源（`ImproveContext` 里没有 provider）；
2. 候选表的排序/截断与路程无关（`reassign` 按**字母序**取前 6 个地点、`relocate` 按时间顺序取空档）；
3. 🔴 **`evaluate` 按块上的 `block.transfer.minutes` 打分，而移动块后全仓没有任何地方重挂提示**
   （`reattachTransfers` 只在 improve 之后跑一次）→ 候选的分数基于旧位置的数据，搜索"看不见"自己。

**决定**
- `ImproveContext` 增 `transfer`，由 solver 注入；aware 档（`scoring='transfer-aware'` 且有 provider）
  候选按步行分钟升序、剪掉走不到的位置；legacy 档逐位不变。
- **评估候选前先重挂提示**（复用 `construct.ts::attachTransfers`），**基线也要重挂**
  （否则基线与候选口径不同，任何移动都会被算成更差）。
- 有意打破 `improve.ts` 顶部「与 construct.ts 无耦合」的声明 —— 只为复用 `attachTransfers`；
  抄一份会漂移的副本更糟。理由写在 import 处。

**验收**：`tests/improve-transfer.test.ts` 3/3，其中主命题用**白盒构造的坏计划**（课在远楼、
自习紧贴其后）断言 aware 会重排而 legacy 不会；反向验证（把 `awareOf` 改恒 false）→ 必红。
`tests/` 109 全绿、`scripts/` 153 全绿、typecheck 0 错、golden 快照逐位不变。

## ADR-009 · churn 的 free 系数由 ×0 改为 ×0.08（规格 §5.5 修订，2026-09-19，CY）

**背景**：`lockFactorOf('free') = 0` 让「最小扰动」只剩度量、没有驱动力 ——
`free` 覆盖的正是**引擎自排的软块**（自习/三餐/活动），也就是用户每次重排时最容易被挪动的那些。
实测：被挤走的块 `churnMin > 0`，但 `cost.parts.churn === 0`（代价为零 ⇒ improve 不会为"少动"让步）。

**决定**：`free` 系数 = `FREE_CHURN_FACTOR = 0.08`（代码常量，注释里写清标定依据）。

**理由**
1. 三级秩序保留：`hard=100`（禁止移动）≫ `soft=1`（明确要求保持）≫ `free=0.08`（别再乱动）。
2. 量级选得**不足以阻止改进**：60 分钟挪动 ≈ 3.84 分，而一次"走不到"的转场罚 20 分、
   一次跨校区块罚 3 分 —— 真正的质量改进照样会被接受。
3. 与冻结快照无冲突：churn 只在传 `previousPlan` 时计，golden 语料不传。

**代价**：三处测试同步更新（churn / p0-check / objective-evaluate），并在注释里注明本次修订 ——
**规格变更必须让原本"钉住旧行为"的测试显式翻新，否则下次有人会以为是回归。**

**对外话术**："引擎原来把'自己排的块'当免费筹码，所以你说'改一下'它就全盘重排。
我们给它定了个价格：动自己排的块要花一点点分——于是它会先找那个'不用动别人'的方案。"

## ADR-010 · 【待决策】improve 的合法性校验粒度：整份计划 vs 只看被改块（2026-09-19，CY 提出）

**现状（已证）**：`improve` 主循环用 `planIsValid(cand.plan, ctx)` 筛候选，而它要求**整份计划**
遵守阶段策略（周末 / 18 点后）。构造出的计划**本就含 8~10 个周末三餐软块**（`weekendWork=false`），
于是**每个候选都被判非法** ⇒ 5 份 golden 语料上 improve **从未评估过任何候选**
（`docs/engine-optimization-paths.md` §三·七 有证据表）。

**已做的实验（结论：不需要改）**：把校验改成「只看候选改动的块」并在 aware 档启用后，
候选**确实被评估了**，但 **接受数仍为 0、计划逐块不变、cost 完全相同**（5/5 语料），
运行时间 ~2×。⇒ 这些计划**本就局部最优**；恒 false 的校验是**掩盖**（让"无改进"与"没在找"
看起来一样），**不是致因**。因此**保持现状**，改动已回退。

**保留的风险点（将来要按此改）**：若 `construct` 将来产出「**可改进**」的计划（新算子、
锁定块写回产生坏排布等），这个恒 false 的校验会**静默关闭**改进阶段，日志只显示"迭代 1、接受 0"。
届时：
1. 加 `Candidate.patched` + 候选级廉价检查，**保留整份校验作接受前兜底**；
2. 在**新档**（`scoring: 'transfer-aware'`）先启用，legacy 保持现状 → 快照继续有效；
3. 跑 `eval:gate` / `eval:engine` / `eval:l3` 对比启用前后，确认方向正确后再讨论翻默认 + 重拍快照。

**建议的落地顺序**（若拍板"改"）
1. 先加 `Candidate.patched` + 廉价检查（只验被改块），**整份校验保留给"即将接受"的移动**（双保险）
2. 在**新档**（`scoring: 'transfer-aware'`）先启用，legacy 保持现状 → 快照继续有效
3. 跑 `eval:gate` / `eval:engine` / `eval:l3`，并对比"启用前后"的 cost 与计划差异
4. 确认改进方向正确后，再讨论是否翻默认 + 重拍快照

**影响面**：`improve.ts` 一个函数 + 一个新测试档；风险集中在"改进阶段第一次真正生效"带来的计划变化。
