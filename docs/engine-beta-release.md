## 四、三处如实说明（不粉饰）

1. **P4 的提速幅度未能量化**。两条独立测量都不支持"大幅提速"：
   ① 墙钟——同一份代码连续两次跑差到 **7×**（transfer-aware 一次 64ms、一次 9.8ms）；
   ② 确定性指标——一次求解的 provider 调用次数**前后完全相同**（week-04-typical：175 / 3561）。
   ⇒ P4 的价值是**行为无损的结构清理**（已由 10 用例指纹逐字对拍证明），
   要拿到性能结论必须**在空载机器上复测**。
2. **P8 的结论被自己的实验推翻过一次**：`planIsValid(整份计划)` 在 5 份语料上恒 false
   （construct 会排出 8~10 个周末三餐软块，而 policy 不允许周末软块）⇒ improve 从未评估过任何候选。
   但把校验改成「只看被改动的块」后，**接受数仍为 0、计划逐块不变** ⇒ 这些计划**本就局部最优**；
   恒 false 的校验是**掩盖**而非致因 ⇒ **改动已回退**。风险点（将来产出"可改进"计划时会被静默关闭）
   与三步改法写入 ADR-010。
3. ~~**默认口径仍是 `legacy`**~~ → **已翻转**（2026-09-19，ADR-007 附记）：
   默认改为 `transfer-aware`。安全性依据：golden 快照走 `buildWeekPlan → construct`、
   **不经过** `solveWeek`，因此快照逐位有效（翻转后 262 个测试全绿，实证）。
   代价：每次求解慢 ~2.7×（19ms → 53ms）；三条降本尝试实测全部否决（§三·八）。
   基线已带 `scoring` 标记。

## 五、术语与口径（后续复测请沿用）

- **计时**：跨时间比 p95/p50 会骗人（机器忙时整体慢 2~3×）。判"是否变慢"必须**同机同刻对照**
  （改动前的树另建一份、同一轮各跑一次），比值在 0.5~1.7 之间属噪声；定论看 p50 且 ≥9 轮。
- **判分**：对自由文本做包含判断前**先归一分隔符/空白**（`_norm()`）；断言本身也要有回归
  （`evals/test_judge_rules.py`），每次假红都先问"是产品错还是断言错"——
  本轮 4 次假红**全部是断言太死**。
- **快照策略**：`legacy` 档逐位保快照；新口径另拍基线并显式标注档位。
