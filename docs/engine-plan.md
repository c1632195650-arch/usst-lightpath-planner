# 规划引擎 · 评估与实施顺序

> 状态：2026-09-11。所有结论基于代码核实（非推测）。
> 适用前提：**前端交互暂缓，先打磨核心逻辑**。

---

## 一、先澄清一个概念问题

原话是「打磨后端，就是整个项目的底层逻辑，比如排程引擎这种」。这里有两个要点需要分开：

| 概念 | 实际归属 | 说明 |
|---|---|---|
| **排程引擎** | **前端纯函数（TS）** | 输入（课表、画像）都在前端 AppState / localStorage；要求即时重算；无 IO、无网络 |
| **梨宝智能层** | 真正的后端（Python） | RAG / 路由 / 记忆 / 空间查询，需要 LLM 与向量检索 |

**结论：「底层逻辑」≠「后端」。** 排程引擎放在前端才合理——放后端会为每次交互增加一次网络往返，且它本身不需要任何服务端能力。

所以正确的抓手描述是：**打磨「逻辑层」**，而逻辑层的主体在前端 TS 侧。

后端在这个方案中的正确位置见 §五。

### 逻辑层 · 缺口

1. **契约缺 4 个类型**：`Phase`（学期阶段）、`WeekPlan`（周计划）、`TimeBlock`（时间块）、`PlanTask`。已确认 `src/lib/planner/` 目录不存在。
2. **没有真正的引擎**：`lbaoRecommend()` 是硬编码填充，不是引擎。
3. **Schedule → 幕墙 blocks 适配层缺失**（Newton 幕墙目前显示 mock 三版）。

### `lbaoRecommend` 为什么是「假引擎」

```ts
blocks.push({ icon: '📖', time: '19:00', ... })   // 时间点硬编码
blocks.push(mealFor(profile))                      // 每天固定加吃饭 + 休息
return { ..., blocks: blocks.slice(0, 5) }         // 每天最多 5 块
```

具体问题：
- **时间点是写死的**（08:00 / 11:45 / 16:00 / 19:00 / 21:30），不随课表变化
- **不用 `slots.weeks`**：无视单双周，第 3 周的课在第 10 周照样显示
- **不处理冲突**：同一时段两门课、跨校区来不及，都不检查
- **不插跨校区缓冲**：`CAMPUS_TRANSFER_MIN` 已定义但未被使用
- **与课表无真实耦合**：只取 `todaysCourses[0]` 当作"上午课程"

它作为概念演示是合格的，但**不能作为产品主干**。

### 智能层 · 已可用

后端 4 个接口（`/api/health` `/api/search` `/api/chat` `/api/memory/reset`），三档路由（grounded / hybrid / llm），三层记忆，60 POI 空间图谱。回归 **9 组 44/44**。

## 三、核心判断：引擎要分两层写

这是整个方案里最重要的架构决定。

| 层 | 性质 | 内容 | 可靠性要求 |
|---|---|---|---|
| **A. 确定性层** | 纯规则、无 LLM、无随机 | 课表铺入时间轴、周次过滤、跨校区缓冲、吃饭窗口、冲突检测 | **100% 可靠** |
| **B. 推荐层** | 画像驱动 + 可选 LLM | 空档填活动、密度/留白、每条给理由 | 允许不完美，**必须可改** |

**为什么必须分开：**

1. **A 层是底线**——课表排错（上错课、漏课）是产品致命伤，必须纯函数 + 单测锁死，不能有任何模型参与。
2. **B 层是差异化**——用户反复强调"人性化、智能化、贴心"，同时又反感"机械、自作主张"。这两者只有在分层后才不矛盾：A 层保证不出错，B 层负责贴心且可推翻。
3. **混在一起写会两头不讨好**：用规则写 B 层会机械；用 LLM 写 A 层会不可靠。

## 四、建议实施顺序

### 第 1 步 · 补契约（`src/types.ts`）

新增 4 个类型，其余不碰：

```
Phase     学期阶段（周次区间 + 该阶段的松紧基调 + 推导依据）
WeekPlan  一周计划（周次 + 7 天 + 每块 TimeBlock + 生成元信息）
TimeBlock 时间块（start/end/type/title/locked/density/candidates/reason）
PlanTask  待办任务（可选，挂靠到时间块）
```

**理由**：这是分工交汇点——队友产出 `Schedule`，引擎消费它，幕墙消费 `WeekPlan`。契约不定，两边各写各的，必返工。
**关键约束**：契约要**以队友已产出的 `Schedule` / `CourseRecord` 为基准反向对齐**，不另立一套命名。

**验收**：`tsc` 通过；队友的解析器产出能直接赋给契约类型，无需适配。

### 第 2 步 · 确定性布局层（`src/lib/planner/layout.ts`）

**输入** `Schedule + 周次 + 画像` → **输出** 一周的确定性骨架（只含课程块 + 缓冲块）。

必须做的事：
- 按 `slots.weeks` 过滤当周课程（修掉单双周 bug）
- 同一时段多门课 → 标记冲突（不自动取舍，交给用户）
- 相邻课程跨校区 → 自动插 `CAMPUS_TRANSFER_MIN` 缓冲块
- 吃饭窗口：只标记"可用窗口"，不硬塞具体时间

**理由**：纯函数、零依赖、可单测。写完就永久有效，改 UI 改后端都不影响它。
**验收**：固定输入断言输出（含周次过滤、跨校区缓冲、冲突检出三类用例）。

### 第 3 步 · 推荐层（`src/lib/planner/recommend.ts`）

在骨架的空档里填内容 + 给理由。升级现有 `lbao.ts`，保留其对外接口形态。

生成**多版本**（这是重点）：
- 不是算"唯一最优解"，而是产出 3–4 个风格不同的版本
- 每块带 `reason`（为什么推荐）与 `candidates`（同类可替换项）
- 密度/留白作为**参数**，不作为教条

**理由**：用户自己点破过——"没有数据或案例能验证算法贴合心意"。既然无法验证"算得准"，就把**「可预览、可选版、可局部调」**做成核心能力。这样即使推荐不准，用户总能挑到接近的，且随时能改。
**验收**：喂入同一份画像 + 课表，产出 3 个版本且互相可区分；每块都有非空 `reason`。

### 第 4 步 · 接通 Newton 幕墙（适配层）

`WeekPlan → 幕墙 blocks`（时间/名称/密度/颜色）≈ 80 行。

**理由**：这是**唯一能让"打磨逻辑"立刻变成"看得见成果"的路径**。幕墙是已有资产（v9），引擎跑出的真实周计划直接投上去，产品立刻从"视觉原型"变成"真实功能"。答辩时说服力完全不同。

**验收**：幕墙显示真实课表（来自队友的 PDF 导入），而非 mock 三版。

## 五、后端在这个方案中的正确位置

后端**不参与**规则计算。它该做的是 LLM 增强，建议**最后做**，且必须可降级：

```
POST /api/plan/suggest
  入参：画像摘要（8 轴 + 场景字段）+ 骨架摘要（哪些空档、多长）
  出参：候选活动 + 推荐理由（自然语言，带梨宝语气）
  降级：无 LLM Key 时，返回本地规则候选集
```

**为什么放最后**：它是锦上添花。现在还没有骨架可增强；先有骨架，LLM 才有东西可润色。

---

## 六、一句话总结

> **先锁契约，再写确定性骨架，然后做可选的推荐层，最后投到 Newton 幕墙上。**
>
> 前两步是纯函数 + 单测，零返工风险；第三步才涉及"智能"，而且以「多版本 + 可调」而非「最优解」为目标；后端只在最后做可降级的 LLM 润色。
