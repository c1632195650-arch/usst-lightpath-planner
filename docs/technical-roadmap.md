## 1. 项目定位与愿景

| 项 | 内容 |
|---|---|
| 产品名 | 上理生活助手（Ugh-Study-Saps-Time / USST） |
| 一句话定位 | 基于**上理本地数据库 + 用户画像**的校园生活智能规划助手（不止学习，覆盖吃、玩、作息） |
| 核心角色 | **梨宝**（AI agent 吉祥物）—— 结合课表 + 画像一键推荐生活方案 |
| 目标用户 | 上海理工大学在读学生（大一/大二优先） |
| 视觉基调 | 上理红校园配色 + 全站卡通化（chill · 有趣 · 贴纸手账），120 周年校庆视觉，**已定稿** |
| 灵魂 | 不制造焦虑。允许"摸鱼"，反对"塞满日程"。可解释、可复现、可降级 |

**为什么从"光溯（纯学习规划）"升级到"生活助手"**：学生的时间不只有课程表，还有吃饭、运动、社交、熬夜。只排学习，产品会沦为第二个"课表 App"。生活助手把画像扩展到 8 轴 + 6 原型 + 8 场景，覆盖完整校园生活。

## 5. 目标架构（分层，避免返工的关键）

```
┌─────────────────────────────────────────────────────────┐
│  前端（Vite + React + TS + Tailwind，PWA）                │
│  展示层：欢迎/画像/月历/周程/倒计时/梨宝面板               │
│  引擎层：画像计分 · 梨宝推荐(规则) · 排程(可选)            │
│  存储层：localStorage / IndexedDB（个人数据，本地优先）     │
└───────────────▲──────────────────────────┬───────────────┘
                │ (个人数据不出设备)          │ (公开数据 + LLM 调用)
┌───────────────┴──────────────────────────▼───────────────┐
│  后端（轻量，Node/Edge Function）                          │
│  · 上理数据库 API（公开信息：食堂/校历/活动/考试节点）       │
│  · 梨宝 agent 服务（规则 + RAG + LLM，输入脱敏）            │
│  · API Key 代理（Key 存服务端，前端不接触）                 │
└─────────────────────────────────────────────────────────┘
```

**核心决策（务必记住）**：

- **个人数据（画像/课表）与公开数据（上理数据库）分两层**。前者本地，后者后端。这样既保隐私合规，又能让梨宝"懂上理"。
- **LLM 只做"自然语言 + 知识检索"，确定性推荐仍由规则引擎出**。理由（沿用 ADR-004）：可解释、可复现、无 Key 可降级。
- **上理数据库优先做成静态 JSON + 版本化**，不必一开始就上数据库服务器；数据量小（几十~几百条），JSON + CDN 或简单 API 即可，后续再迁数据库。

## 7. 数据库与梨宝 agent 搭建专项（核心难点）

### 7.1 上理数据库 schema（建议，JSON 起步）

```ts
// 食堂
interface Canteen { id; name; campus; tags[]; price; openHours; crowd; rating; note }
// 自习点
interface StudySpot { id; name; campus; seats; openHours; quiet; wifi }
// 活动
interface Activity { id; name; type; time; place; target; source }
// 校历
interface SchoolCalendar { year; terms[]; holidays[]; examWeeks[]; keyDates[] }
// 考试/时间节点
interface Deadline { id; date; title; tag; note; source }
// 培养计划
interface TrainingPlan { major; courses[]; credits }
```

### 7.2 信源采集（公众号 → 结构化）

| 信源 | 内容 | 采集方式 |
|---|---|---|
| 上理官方公众号 / 校官网 | 校历、校庆、重大通知 | 人工整理 + 结构化 JSON（数据量小，先不自动化爬取） |
| 光电学院 / 学生会公众号 | 讲座、竞赛（光电杯等）、活动 | 同上 |
| 教务处 | 选课、考试安排、培养计划 | PDF/公告人工录入 |
| 团委/志服部等 | 社团招新、志愿活动 | 同上 |

> **采集策略**：v1 阶段**人工整理成 JSON**即可（几十~几百条），追求"准"而非"全"。自动化爬取/同步是 v2+ 的事，且要规避公众号版权与频率限制。

### 7.3 梨宝 agent 架构

```
输入：用户画像(8轴+场景) + 课表 + 选中日期 + 意图(mod 或 自由提问)
   │
   ├─ 确定性规则引擎（可解释、可复现、无 Key 可用）
   │    画像打分 → 选生活模式 → 生成日程块（课程/自习/三餐/活动/休息）
   │
   └─ LLM 层（自然语言 + 知识检索，可降级）
        ① 脱敏网关（过滤学号/姓名/班级/教师）
        ② RAG 检索上理知识库（食堂/自习/活动/校历）
        ③ 生成人话解读 + 开放式问答
   │
输出：日程建议 + 可解释理由 + （可选）对话回复
```

**为什么规则 + LLM 双轨**（延续 ADR-004）：评委问"算法依据是什么"时，规则引擎能逐项拆解；LLM 只负责"把话说得像人"，且必须可降级——无 Key、无网络时产品完整可用。

## 8. 关键决策与风险

| # | 决策/风险 | 结论 |
|---|---|---|
| 1 | 个人数据本地 vs 后端大模型的张力 | **分层**：个人数据本地优先，公开数据 + LLM 走后端。二者物理隔离 |
| 2 | 纯前端要不要上后端 | 要，但**只上轻量后端**做三件事：数据库 API、LLM 代理、脱敏。不做重型账号 |
| 3 | 上理数据库要不要上真数据库 | v1 用**静态 JSON + 版本化**，量级起来再迁 SQLite/Postgres |
| 4 | 光电杯 9/28 时间点 | 若仍参赛：阶段 1 是参赛级最小可用（真实校历+PDF课表+真实数据库），阶段 3 LLM 可赛后补 |
| 5 | PDF 格式不稳定 | 手动录入兜底，不卡死；先取真实样本校准 |
| 6 | 公众号信源版权/频率 | 人工整理、注明来源，不做高频爬取 |
