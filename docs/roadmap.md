# 产品路线图（Roadmap）

> 本文回答三个问题：**功能怎么分类、按什么顺序做、HTML 怎么走到 App**。
> 模块级契约见 `docs/features.md`（M0–M9）；本文是更高一层的"地图"。
> 状态约定：`P0 必做` / `P1 该做` / `P2 远期` / `⛔ 砍掉`

---

## 0. 三条总原则（所有决策以此为准）

1. **MVP = 一条能跑通的主线 + 一个记忆点**，不是功能多。记忆点 = **反内卷排程**（考试周留白率不降反升）。
2. **HTML 优先，App 后置**。全程只做 Web（响应式 + PWA），App 走 PWA → Capacitor 路线，20 天内不碰原生。
3. **课表以 PDF 导出为主输入**（教务系统能导 PDF，用户拖进来即解析），粘贴/手动作为兜底。

## 3. HTML → App 移植策略

**结论：20 天内只做 Web + PWA，不碰 App。** 移植是"正式上线"阶段的事，且成本可控。

| 阶段 | 方案 | 成本 | 何时用 |
|---|---|---|---|
| **现在（MVP）** | **PWA**：响应式 + manifest，可"添加到主屏幕"、离线可用 | ≈0，一行代码不加 | 答辩话术"一套代码覆盖双端、可安装、可离线" |
| **正式上线** | **Capacitor**：把现有 Web 打包成 iOS/Android 原生壳 | 低（几小时），复用 100% Web 代码 | 想上应用商店、要推送/本地通知时 |
| **需要原生能力** | React Native / Flutter 重写 | 高（重写） | 需要 GPS、蓝牙连 ESP32、后台定位等 Web 给不了的能力时 |

**为什么先 HTML**：
1. 迭代快，改一行立即刷新，2 个小白 debug 成本最低。
2. PWA 已覆盖"手机主屏打开"这个核心诉求。
3. 若被评委问"为什么是网页不是 App"，答：*"本地优先架构 + PWA，数据不出设备、离线可用，后续用 Capacitor 无痛打包双端。"*

## 4. PDF 课表导入专项（本轮新增重点）

**为什么 PDF 是主通道**：上理工教务系统支持导出 PDF 课表，用户"导出→拖进网页"最顺手，比粘贴文本/CSV 门槛低、且是通用 App 不会做的我校定制点。

**技术方案**：
- 用 `pdfjs-dist` 在前端解析 PDF（纯浏览器，不碰账号密码、不上传服务器）。
- 抽取出文字后，按"星期 × 节次"网格还原成 `Course[]`（day / 节次 / 课程名 / 地点 / 教师 / 周次）。
- 地点字段 → `constants/campus.ts` 里的教学楼→校区推断，自动算跨校区转场。

**风险与兜底**：
- ⚠️ PDF 格式固定但需**真实样本校准**；不同浏览器对 pdfjs 兼容有差异。
- 解析失败 → 必须退回**手动录入**（P0 兜底），不许卡死在 PDF 上。
- **D3 前取 1–3 份真实 PDF 课表样本**（含跨校区课程），这是 B 的开工前置。

**负责人**：B（`src/lib/parseSchedule.ts` + `src/features/schedule/`）。

## 5. MVP 范围（本轮先做，就这 4 件）

| # | 功能 | 模块 | 一句话验收 |
|---|---|---|---|
| 1 | PDF 课表导入 | M2 | 拖入 PDF → 生成正确课表；失败能手动录 |
| 2 | 学期五阶段可视化 | M3+M5 | 看到 5 段 + 留白率曲线 |
| 3 | 周/日排程 + 强制留白 | M4+M5 | 明显留白，考试周留白反而更多 |
| 4 | 轻量问卷画像 | M1 | 8–10 题 → 影响排程权重 |

**MVP 演示脚本（2 分钟）**：拖 PDF → 出学期阶段图 → 填问卷 → 展示留白周排程 → 切期末倒计时。

**明确不做**：光感知硬件、社区/搭子、食堂/地图、AI 大模型、原生 App——全部 P2 或暂缓。
