01 · 项目概况

一个懂上理的智能决策伙伴

校园知识问答（RAG）＋ 画像 ＋ 排程引擎 ＋ 移动端。技术上是一条「数据 → 检索 → 对话 → 排程 → 执行」的完整链路。

项内容
项目名称光溯 · 上理生活助手（usst-lightpath-planner，v0.4.9）
参赛赛事第 18 届光电杯创新设计大赛（光电学院学术部主办）· 主题「智逐光影，溯梦未来」
团队2 人（CY：产品/数据/梨宝线；RAY：周排程算法/周视图）＋ AI 协作开发
技术栈TypeScript / React / Vite / Tailwind · Python FastAPI · SQLite（FTS5＋向量）· Capacitor / Android
部署形态公网 Web（nginx＋systemd）· 签名 APK 直装 · ICS 订阅 · 云同步

定位的三次演变（2026-09-15 定稿）

版本定位转向原因
v1反内卷排程工具（纯前端）把排程当主干，「留白率」为核心主张
v2梨宝校园 AI 助手（＋后端＋RAG）「贴心」本质是伙伴而非工具；规则引擎撑不起开放问答
v3（终）懂上理的智能决策伙伴排程只是一种输出形式；确立「懂上理 / 懂你 / 懂分寸」三钩子与 L1–L4 边界（L4 决策层绝不做）

07 · 协作与工程过程

双人分工，三层人机结构

双人协作

所有权表分工：CY 负责画像 / 梨宝 / 后端 / 数据 / 文档，RAY 负责周排程 / 引擎 / 组件；接壤处仅留一个冻结接口。RAY 两度以独立分支交付（09-20 第四轮 UX、10-08 五批），合并口径为「底层与实现逻辑以 Ray 的提交为准」。10-02 起转单人主导。

三层人机结构

人类拍板 ＋ AI 军团执行 ＋ 独立验收（MOSS）。人类负责所有需求歧义与契约拍板（BLOCKERS 中「需要人决定」逐条留痕）；AI 承担无人值守通宵批次（6+ 份夜战报告存档）；验收角色独立于执行。

AI 贡献占比说明：commit 作者署名统一为「光溯开发组」，无法按作者精确拆分；从台账与 commit 内容判断，代码主要由 AI 会话在人类逐批授权与验收下产出（Ray 的周页 / 目标批为其本人提交后接入）。
