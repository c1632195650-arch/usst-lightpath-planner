### 1.1 背景一句话

手机端已能记录待办与目标（D1），但**网页端看不到、也不能排**。闭环缺最后一环：用户在手机写「这周读完《学习之道》」，网页端 AI 排计划时**不知道这件事存在**。本批建网页端待办工作区，并让待办**真正参与排程约束**。

**CY 的原话**（验收唯一标准）：

> "加完过后可以不用在app上本地排，可以记着空了登上网页版过后要能同步再让ai或者它自己排，**这一系列流程一定要打通实现用排闭环**"

> "涉及到主网页端备忘的功能和 数据与闭环也要另外立一个方案（跟移动端的区分开）"

> "待办就分**最近待办**和**中长期待办**（待办可以在完成时要求填写具体完成时间（粗糙一点比如2026年九月上中下旬这种）**最近待办就不需要了**，一般办好就打勾，长期的是怕用户忘掉完成时打勾而设定的）"

### 1.2 🔴 核查发现：网页端**已有两条引擎通道**，本批是"接上"不是"从零造"

这是本轮最重要的发现，**决定了工作量远小于预期**：

| 通道 | 定义 | 现状 |
|---|---|---|
| **`UserTask`** | `src/lib/planner/templates.ts:334`，字段：`id/title/emoji/kind/category/dayOfWeek/startMin/durationMin/weeks/place` | ✅ 引擎支持｜✅ 网页端**已有 UI 入口**（`src/features/week/AddTaskPanel.tsx`）｜✅ store 已支持（`userPlanStore.ts:133 tasks` / `:195 addTask`） |
| **`Commit`** | `src/lib/planner/model.ts:85`，字段含 **`effortMin`（时长）**/**`dueAt`（交期：周次+星期+分钟）**/**`splittable`（可拆分）**/`window`/`placeId`/`priority` | ✅ 引擎支持（`solver.ts`/`construct.ts`/`objective.ts`/`incremental.ts`）｜❌ **无任何 UI 入口**（只被 `lib/planner/` 内部消费） |

**结论**：
- **短期待办** → 走 `UserTask`（网页端已有完整链路，最省力）
- **中长期待办** → 走 `Commit`（有 `dueAt` + `splittable`，正是"本周累计做完"的语义）

>📌 **这避免了重复造轮子**：本批**不需要**新建引擎通道，只需要「待办 UI → 映射到这两条通道 → 排程时当约束」。
